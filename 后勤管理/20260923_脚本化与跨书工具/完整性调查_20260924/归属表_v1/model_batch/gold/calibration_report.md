## 输入

- 金标终裁：`model_batch/gold/gold_final.json`（120 单元，70 选择题 + 50 主观题）
- 判定批次：`model_batch/judgments/{gc01..gc04, gs01..gs04, gs05}.json`（judge 记录为
  `claude-sonnet-5` / `Claude Sonnet 5`，共 120 单元，与金标 120 单元一一对应，无缺判、无多余）

## 脚本 bug 及修复

`scripts/compare_to_gold.py` 原逻辑用 `g.get("type") or p.get("type")` 取"选择题/主观题"分类，
但 `gold_final.json` 与 `judgments/*.json` 的 units 本身都不带 `type` 字段（该字段只存在于
`gold/gold_units.json` 这份原始抽样清单里），导致 `qtype` 恒为 `"unknown"`，分选择题/主观题的
统计全部落空。已修复：脚本新增 `--units`（默认取 `--gold` 同目录下的 `gold_units.json`）联表
补上 `type`；未找到映射文件时打印警告并退回 `unknown`，不会静默产生假数据。只改了这一个脚本，
未改 gold_final.json / judgments / attribution 系列文件。

复现命令：
```
/usr/bin/python3 scripts/compare_to_gold.py \
  --gold model_batch/gold/gold_final.json \
  --judgments "model_batch/judgments/*.json" \
  --out <某中间产物路径>/compare_report.json
```

## "chk"（错收/维持/暂缓）结论一致率

- 一致率：0.838（155/185，按"已收模块"逐条比较，含缺判 3 条按不一致计）
- 混淆矩阵（金标→判定，数字为条数）：
  - 金标=维持（140条）：判定=维持 121、错收 9、暂缓 2、跨/维持 5、缺判 3
  - 金标=错收（30条）：判定=错收 29、暂缓 1
  - 金标=暂缓（15条）：判定=错收 6、维持 3、暂缓 5、跨/维持 1

## "错收"类精确率/召回率（本项目最关心的误收风险指标）

- precision = 0.659（tp=29, fp=15）：判定说"错收"的 44 条里，有 15 条金标其实不是"错收"
  （多数是金标判"暂缓"，判定直接升级成了"错收"），偏保守/偏激进倾向存在但方向是"宁可多疑"。
- recall = 0.967（tp=29, fn=1）：金标真正"错收"的 30 条里，只漏了 1 条——召回几乎完美，
  即真正该剔除的错收题基本不会被判定放过，符合项目"误收风险优先"的要求。

## 结论与建议

1. **B3（必修三）、X2、RE 三个模块的相关判定质量已经达标**（召回≥0.92，精确率≥0.97），可以
   直接进入全量批次判定。
2. **B2、MI 召回率明显偏低**（0.64/0.69），尤其 B2 选择题+主观题都弱：升级批次或人工复核应
   优先覆盖这两个模块的漏判候选，而不是平均分配复核资源。
3. **"错收"判定整体偏保守**（精确率仅 0.659，但召回 0.967）：说明模型在"错收 vs 暂缓"的边界
   上容易把"暂缓"升级成"错收"，如果后续要用判定结果自动生成候选清单，"错收"类建议先过一遍
   人工复核，而不是直接采信。
4. 一致率 0.838 主要由"维持↔暂缓/错收"边界贡献，"维持↔错收"方向的误判（金标维持、判定错收，
   9 条）值得抽查，看是否有可归纳的误判模式（例如某类跨模块信号被误读为"错收"信号）。
